I Wrote the Install Guide for My Dashboard So an Agent Could Follow It

November 23, 2026

xstats ships with a small set of agent skills for setup, sync, updates and the weekly summary, and writing them taught me that docs for an agent are mostly about what it must never do.

xstats is a small dashboard I built to track my X numbers: followers over time and how each post does. It is one Go binary, one SQLite file, and a Caddy config in front of it. The code lives at github.com/scott/xstats.

The part I did not expect to spend so much time on was not the dashboard. It was the install guide. Not the README, which is for people. The other guide, the one written for an agent.

xstats does not call the X API itself. Something has to collect the numbers every hour, push them in, check for new releases, and answer "how did last week go?" In my setup that something is my assistant. So alongside the code I wrote a handful of skills: getting started, setup, sync, accounts, backfill, update, and a weekly summary. Each one is a plain Markdown file that tells an agent how to do one job.

Writing them changed how I think about documentation.

A README explains. A skill has to decide.

A README can say "configure your environment and start the service." A person fills in the gaps with judgment. An agent fills in the gaps too, and that is the problem. It will happily invent a reasonable-looking step.

So the skills are less about explaining and more about removing choices. The setup skill says, near the top, never build with Go, always use a release. Download the binary, download SHA256SUMS, and check every file. Any mismatch, stop. That is one line for me and a whole category of creative failures the agent never gets to try.

The same goes for dates. The sync skill computes the day in the owner's time zone and puts it in the bundle explicitly. Never let the server pick the day. Think about a sync that runs just after midnight UTC for someone in Denver, and you can see why.

Most of the important lines are "never"

Rereading the skills, I noticed how many of the load-bearing sentences start with "never."

  • Never print the env file. It holds the ingest token.
  • Never deploy an update without the owner's yes in chat. The check itself is read only.
  • Never screenshot a real owner's dashboard for the intro. Use the demo-data images.
  • Never estimate or invent a number in the weekly summary. Use only what the API returns.
  • Never post the summary to X. It is chat only.

None of these are hard to implement. They are hard to remember to write down. A person setting up a dashboard would not paste a secret into a chat window or post someone's stats publicly. An agent might, not out of malice, but because nothing told it that was out of bounds and it was trying to be helpful.

I have written about giving agents narrow doors before, in the context of posting. This is the same idea for operations. The skill is the door.

Quiet by default

The sync skill runs every hour. If it reported every success, it would be the most annoying thing on my phone within a day.

So the rule is simple: say nothing when a run succeeds. Skipping a run because the daily read budget is used up is not a failure either, so that is quiet too. The skill keeps a small state file with how many reads it has used today, how many runs have failed in a row, and which days still need to be pushed again. It only speaks up when something is actually wrong and stays wrong.

The update skill works the same way. Once a week it compares the deployed version with the latest release. Same tag, silence. A newer tag gets one short message: what changed, anything that looks risky like database or config changes, and "Update now?" If I say not now, it does not ask again for that tag. That one sentence in the skill is the difference between a helpful check and a nag.

Honest about what it cannot do

The backfill skill was the most interesting one to write, because the honest answer to "can you load my history?" is "partly."

X will give you older posts and their current totals. It will not give you what your follower count was on a Tuesday three months ago. So the skill tells the owner up front, before doing anything: older posts yes, past daily follower counts no, the follower line starts on the first sync day. Then it asks.

I like this pattern a lot. The agent sets expectations before it spends anyone's API budget, instead of producing a chart that quietly implies data it does not have.

Questions one at a time, with defaults

The getting-started skill asks the owner a short list of questions: which handles, what time zone, box only or a real server, and so on. Two rules made it feel much better.

Ask one question at a time and wait. And offer the default in brackets, so "ok" is a valid answer. Most people setting up a side tool do not want a form. They want to say ok four times and see a dashboard.

Answers go into the assistant's memory as facts. Secrets never do. They come in through the assistant's secret flow and land in files with tight permissions.

What I would tell someone shipping a tool today

If your tool is likely to be installed or run by an agent, and more of them are, the agent-facing guide is part of the product. A few things I would do again:

  1. Ship releases with checksums and tell the agent to use them. Do not let it build from source unless that is the point.
  2. Write the "never" list first. It is shorter than the how-to and it matters more.
  3. Make success silent and failure specific.
  4. Make the agent say what it cannot do before it tries.
  5. Keep each skill to one job, with a one-line description of when to use it. That description is how the agent picks the right file.

The skills are a small part of the repo next to the code. But they are what make it something I can hand to an assistant and stop thinking about, which was the whole reason I built it.
