I Gave My Agent's Posting a $20 Monthly Budget, and the Scheduler Fails Closed

November 19, 2026

Putting a hard dollar cap and known per-post prices into the tool my agent posts through changed how it writes, and the most important rule was that missing numbers mean nothing posts.

When an agent can do something that costs money, the question I care about is not how smart it is. It is what happens on the day it is wrong.

My agent drafts posts for my X account. It sends them to xpost, a small scheduler I run at post.scottmiller.io, and I approve each one before it goes out. xpost talks to the official X API, and the X API charges per post. So once I wired it up, every approved draft had a price.

The prices are small. A plain text post costs about $0.015. A post with a URL in it costs $0.20. Images and alt text are $0.005 each. I set a monthly cap of $20.

None of that sounds like a big deal, and it is not, at the scale of one person posting a handful of times a day. But the way I built the cap taught me more about building agent tools than the money ever will.

The cap is not advice

The first version of a budget is usually a sentence in a prompt. "Try to keep costs low." "Avoid links unless needed." I have written lines like that, and they do something, but they are not a budget. They are a hope.

In xpost the cap is enforced in code, in two places.

The first is when I approve a draft. Before a draft can be scheduled, xpost estimates what it will cost, part by part, including any images and alt text. That estimate has to fit inside the cap minus what has already been spent this month minus what is already approved and waiting in the same month. If it does not fit, the approve button is blocked and the page says why.

The second is the dispatcher, the only piece of xpost that actually calls X. Before it posts anything, it checks a gate. A cap has to be set, the rates have to be known, and the month has to be under the cap. Then, per draft, the remaining cost has to fit. If any of that fails, nothing posts, and the Log and Settings pages show the reason.

The approve-time check is the friendly one. The dispatcher gate is the backstop. I wanted both, because the friendly check can have a bug and the backstop still holds.

Missing numbers mean no

The rule I am happiest with is the boring one. If the cap is unset, or a rate is unset, xpost does not guess. It fails closed.

That sounds obvious written down. It is easy to get wrong in practice. The tempting default is "no cap configured means unlimited," because that is what makes the first demo work. But a fresh install, a bad config edit, or a deploy that drops an environment variable all look exactly like "no cap configured." I do not want any of those to quietly turn into "post whatever you have."

The same idea applies to images. If the upload rate is not set, drafts with images are held. If the alt text rate is not set, drafts with alt text are held. A post that cannot be priced does not go out.

I think this is the right default for any agent tool that spends money or does something hard to undo. Unknown should be treated as no, and the tool should say clearly why it said no.

Prices change what the agent writes

The part I did not expect was the effect on the drafts themselves.

Once the agent's instructions include the actual numbers, it writes differently. A link is more than ten times the cost of a plain post. So the agent keeps links for the posts that need them, and a lot of posts do not. A post that makes its point in plain text, with the link in a reply or not at all, is usually a better post anyway.

That is the general lesson I keep relearning with agents. Vague guidance gets vague behavior. Real constraints, with real numbers, get decisions. "Be thrifty" is a vibe. "$0.20 versus $0.015, and $20 for the month" is something the agent can reason about, and something I can check.

It also makes my review easier. When a draft has a link, I can ask one question: is this one worth the higher price? Most of the time the answer is clear.

Spend is a number I can see

xpost keeps a post log with a cost estimate for each item. So the budget is not a feeling, it is a page. As of this week, the month's spend is still under a dollar against the $20 cap.

That low number is not the point. The point is that I do not have to wonder. If my agent's habits changed, or I approved more link posts than usual, I would see it before it became a surprise.

Never pay twice by accident

The other place money and agents get messy is retries. Networks fail. A call to X can time out after it actually went through. A naive retry posts the same thing twice, and on a paid API it charges you twice too.

xpost writes an intent row before each X call. The outcome moves it to posted, retry, failed, or unknown. Unknown is the ambiguous case, where xpost cannot tell whether X accepted the post, and those are never re-sent automatically. They wait for me to look. A retry also skips any parts of a thread that already posted.

That costs me a little convenience on a bad network day. It saves me from the worst version of an agent mistake, which is the one that repeats itself.

What I would carry to any agent tool

If I were building another tool that lets an agent spend money, I would start with the same short list:

  • Put the prices where the agent can see them, as numbers, not adjectives.
  • Enforce the cap in code, at approval time and again at the moment of spending.
  • Treat a missing cap or a missing price as a hard stop, and show why.
  • Record intent before the expensive call, and never auto-retry an ambiguous one.
  • Make spend visible on a page a person actually looks at.

None of this is clever. That is the appeal. The agent can be as creative as it wants with the words. The money follows rules that do not depend on the agent being right.
