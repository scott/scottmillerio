In My Family App, Every Agent Borrows One Person's Permissions

November 26, 2026

When I built Kin, a small private app for my household's people, dates and providers, the most important design rule was that an agent never gets its own access, only a slice of the person who owns it.

I built a small private app for my household called Kin. It keeps track of the people we care about, the providers we rely on (doctors, the vet, contractors, school), the dates we should not forget, and the calls made on the family's behalf. It is the same shape as my other side projects: one Go binary, one SQLite file, Caddy in front, on the smallest droplet I could pick.

What made Kin different was not the stack. It was who uses it. Every person in the house gets their own login, and so do my agents. I have an assistant that reads my inbox, one that helps with the calendar, and bots that place calls. All of them are useful inside an app like this. All of them are also exactly the kind of thing that should not be able to see everything.

So the rule I started from, before any screens, was simple: an agent never has its own access. It borrows a slice of one person's.

An agent belongs to a member

In Kin, every agent belongs to one household member. It acts with that member's visibility, never more. If I can't see a record, my agent can't either. If my agent has a narrower scope than I do, it sees less than I do.

That sounds obvious when you write it down. It is not how a lot of integrations work. The common pattern is a service account or an API key that sits beside the users with its own, usually generous, permissions. That is convenient right up until you have to answer the question "what could this thing have seen?" With a service account, the honest answer is often "all of it."

When the agent borrows a person's permissions, the answer is "whatever that person could see, minus what the scopes took away." That is a question I can actually answer.

It also means the role model does real work. Kin has owner, admin, adult, teen and guest roles. Teens and guests can't own agents at all. A permission to read sensitive numbers can only be granted to an agent by a member whose role can see those numbers in the first place. You can't hand down what you don't have.

Scopes are small, and most of them read

The scopes are deliberately boring. There are read scopes for the things an agent needs to look up, and a few narrow write scopes: logging a call, appending an activity like a gift or a visit, and proposing a suggestion.

What's missing matters more than what's there. There is no edit scope and no delete scope. There is no scope for writing general notes. There is no calendar write scope inside Kin, because my calendar assistant already owns calendar writes elsewhere and I didn't want two places that could change the same thing.

The most useful write scope is the one that doesn't really write. When my inbox assistant sees a new contact in email, it can only propose that person through a suggestion. Nothing lands until a human approves it in a review queue: add as new, merge into an existing person, or dismiss. Kin checks for likely duplicates by email, phone and name when the suggestion comes in, so the review is a quick decision rather than detective work. Gift ideas an agent finds go through the same queue. Only real events, like a call that happened or a gift that was actually bought, get written directly, and those are append only.

I have written before about giving agents a narrow door for posting. This is the same idea applied to data. The agent gets to knock. A person opens the door.

Hidden looks exactly like missing

One small rule I'm glad I made early: a record you can't see answers 404, the same response as a record that doesn't exist.

That applies to people in the house and to agents. An agent probing ids can't tell the difference between "there is nothing here" and "there is something here you aren't allowed to see." For a family app that holds health-adjacent provider details and private notes, the existence of a record can be information on its own.

Scopes are also checked before any lookup. If a token doesn't have the right scope, Kin doesn't go find the record first and then refuse. It refuses before it looks.

To keep that honest, there is one visibility function that decides whether a viewer can see a record, and an equivalent SQL filter used for list pages. The tests check the two against each other across a pile of generated records, so a list page can't quietly show something the detail page would hide.

Tokens you can reason about

Agent tokens are shown once, when they're created or rotated. Kin stores only a hash and a short prefix, which is enough to recognize a token in a log without being able to use it. Rotating revokes the old token immediately. Revoking the agent, disabling its member, or taking away that member's right to own agents stops its tokens too. A token in a URL is refused. It has to come in the Authorization header.

Each token also has daily limits on reads and writes, and an hourly cap on suggestions. None of my agents come close. The limits are there for the day one of them gets stuck in a loop at 3 AM.

Every agent gets a page

The feature I use most is the least technical one. Every agent has its own page showing who owns it, its token status, its scopes, its limits, and a feed of everything it has done: suggestions, activities, calls and API requests. People's records show "Added by" with a link back to that page.

Behind it, every authenticated API request writes an audit row with the member, the agent, the token, the method, the path and the records it touched. I don't read the audit log for fun. I read the agent page. But knowing the full log is there is what lets me be relaxed about adding a new agent.

What I'd tell anyone building for agents

If your app is going to have agents as users, and more apps are, I'd start with three questions before designing anything else:

  1. Whose permissions does this agent borrow? If the answer is "its own," think hard about why.
  2. What can it do without a person saying yes? Keep that list short and append only.
  3. Where do I go to see everything it did? If that takes a database query, build the page.

None of this made Kin harder to build. Most of it is a few tables and one carefully tested function. It just has to be decided first, because retrofitting "the agent can only see what its owner sees" into an app that started with a shared API key is a much worse week than writing it in on day one.
