Agile Was Built for Expensive Code

October 22, 2026

When agents write most of the code, the hard part of agile shifts to intent, context, guardrails and verification. Here's what I think changes and what stays.

For most of my career, the scarce thing on a software team was implementation. We had more ideas than hands, so the whole process was built around rationing engineering time. Story points, capacity planning, two-week sprints, grooming sessions. All of it exists to decide which small slice of the backlog gets built next.

That constraint is going away. When an agent can turn a clear request into a working change in minutes, building isn't the bottleneck anymore. The hard parts are now everything around the code: saying clearly what you want, giving the agent enough context to do it right, setting the limits it has to stay inside, and checking that what came back actually works.

I think that shift changes how agile should work more than any framework debate does.

Two camps, one shared observation

The conversation right now splits roughly in two.

One camp says agile's principles still hold. Inspect, adapt, work toward clear goals, keep feedback loops short. What has to change is the practices, because ceremonies designed around human typing speed don't fit a team where agents do most of the typing.

The other camp says agile is structurally obsolete and wants something new in its place. One proposal I've seen called Agent-Driven Development makes intent the unit of work, and the humans act as editors and orchestrators instead of implementers.

I lean toward the second camp. I think agile's practices were built around rationing human implementation time, and once that constraint is gone, patching the ceremonies one at a time leaves you with a process designed for a problem you no longer have. I'd rather build around intent from the start than keep renaming sprint rituals.

The two camps still agree on more than they admit. Both say the human job is moving toward judgment, verification and system design. Both say "done" has to mean evidence, not a status change on a ticket. Where they split is whether you get there by adapting agile or by replacing it, and I think replacing it is the more honest answer.

Sprints get shorter, or go away

A two-week sprint made sense when two weeks was roughly how long it took to build a meaningful batch of work. When an agent can do a batch overnight, a fixed two-week box starts to feel slow.

Teams are trying a few things. Some run daily cycles where agents work overnight and humans review during the day. Others drop the box entirely and move to continuous flow, where work gets pulled, built, reviewed and shipped one item at a time.

I don't think there's one right cadence yet. What I'd watch is where work piles up. If finished agent output sits waiting for review for days, the cycle length isn't the problem. Review is.

Planning becomes writing down intent

This is the change I find most interesting. In a lot of teams, planning meant breaking work into tasks and estimating each one. Planning poker, capacity math, arguing over whether something is a 3 or a 5.

Estimation matters a lot less when implementation is cheap. What matters more is whether the request is clear enough that an agent builds the right thing the first time. Some people call this Intent Design: define the outcome, the success criteria, the constraints, and how much the agent is allowed to decide on its own.

In practice I think that looks like a short written plan for each piece of work:

  • What should be true when this is done.
  • How we'll know, in terms someone can check.
  • What the agent must not touch.
  • Where it should stop and ask instead of guessing.

That plan is also the cheapest place to catch mistakes. Fixing a wrong assumption in a few lines of text takes a minute. Fixing it after an agent has built on it takes much longer, and it takes a review cycle on top. So I'd rather spend planning time reading and pushing back on the plan than estimating tasks.

Grooming gets lighter

Backlog refinement used to mean long tickets and long meetings. Some of that is going away on its own. Agents can help break work down, flag tickets that are missing acceptance criteria, and point out when two items overlap.

What doesn't go away is the need for a sharp definition of the work. If anything, strong specs, quick prototypes and clear acceptance criteria matter more than ever, because the agent will happily build exactly what you wrote, including the parts you didn't mean. A long ticket isn't the goal. A clear one is.

The human job changes

If the agents are implementing, the people on the team spend their time on other things:

  • Editing and orchestrating: deciding what gets built, in what order, by which agent.
  • Verifying: reading plans before work starts and checking results after.
  • Owning the system: architecture, quality bars, and the guardrails agents work inside.

I think this is the part teams underestimate. Reviewing agent work is real work, and it doesn't shrink just because the code got cheaper. If anything there's more to review. The teams that do well will be the ones that decide on purpose where human attention goes, instead of letting it get spread thin across every diff.

Done means evidence

The Definition of Done is getting stricter, and I think that's healthy. "The agent says it's finished" is a claim. Done should mean there's something a person can check: tests that ran, logs, a screenshot of the feature working, a review that signed off against the original plan.

That last part is the one I'd push hardest on. A review only means something if it checks the work against what was agreed before the work started. Otherwise you're just reading the agent's summary and hoping.

Agents as their own workstream

One more pattern I'm seeing: teams treating agents as a parallel workstream with its own rules. Agents get their own capacity budget, a named person responsible for each one, and their own evidence requirements before anything merges.

I like this because it makes the cost visible. Agent work isn't free. It costs compute, and more importantly it costs review time. Giving it its own lane on the board means someone has to decide how much of it the team can actually absorb.

What I'd actually change first

If I were running a team today, I wouldn't spend time tuning sprints. I'd build the process around intent, starting with three changes:

  1. Replace estimation with a short written plan per item, reviewed by a person before any agent starts.
  2. Make "done" mean evidence that someone can check in a couple of minutes.
  3. Track where review time goes, and shorten the cycle only as fast as review can keep up.

Short feedback loops and adapting to what you learn are still worth keeping. But I think the process agile built on top of them assumed code was the expensive part, and that's no longer true. The feedback loop used to run through the code. Now it runs through the intent you write down before the code exists, and the evidence you check after. I'd design the process around that directly instead of retrofitting sprints to fit it.
