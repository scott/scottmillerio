I Wanted Creating an Agent to Feel Like Creating an App

November 5, 2026

Getting an agent to answer in a chat is the easy part. Shipping one that is reachable, versioned, and safe with credentials is the gap I built Cast Agent to close.

Getting an agent to answer in a chat session is not that hard anymore. You pick a model, write some instructions, wire up a tool or two, and it works. On your laptop. In that terminal. Until you close the window.

The gap I kept hitting was everything after that. I wanted a real agent: something reachable on a URL, with credentials handled carefully, a place to host it, and a path to change it later without rebuilding from scratch. That part still felt like stitching together half a dozen one-off scripts every time.

So I built Cast Agent. It is a CLI and terminal UI for creating, testing, and deploying AI agents. The job I wanted it to do, in one line: describe what the agent should do, get a scaffold, deploy it with one command to a provider I already use.

The painful middle

By hand, the middle of agent work was always the same list.

First you invent a project shape. Instructions in one file, tools in another, config somewhere else, a runtime that speaks whatever protocol you picked that week. Then you figure out secrets. Where do the API keys live so they are not printed into a YAML file you will accidentally commit? Then you pick a host. Docker on this machine is fine for a demo. For something other people can hit, you want Railway, Fly.io, a DigitalOcean droplet, or something else you already have credentials for. Then you change the agent, and you have to remember how you deployed it last time, and whether the old version is still running somewhere.

None of that is interesting AI work. It is the same glue every app needs, except the agent ecosystem still treats it as optional homework.

I got tired of doing the homework twice for every agent I wanted to keep around.

Describe, scaffold, deploy

Cast Agent starts from a description. You say what the agent should do, and the interactive builder scaffolds it: instructions, tools, and configuration, ready to develop. The runtime is Python-based and speaks the A2A protocol, so the thing you end up with is an A2A server, not a one-off chat script.

Deploy is one command against a provider you choose. Local with no container, Docker on this machine, Railway, Fly.io, a DigitalOcean droplet, DigitalOcean MicroVM, or Sprites. Cast does not run its own microVM fleet. The providers do. Cast just knows how to hand your agent to them.

That split matters to me. I did not want to become an infra company in order to make agent creation feel less painful. I wanted the create path to feel closer to create-app, and the host to be whoever I already trust for that kind of compute.

Why the provider list is the point

Different agents want different shapes of machine.

Sometimes local is enough. You are iterating, you do not want a network hop, and Docker is optional. Sometimes you want a managed container with an automatic deploy story, which is why Railway and Fly.io are there. Sometimes you already live on DigitalOcean and a droplet with Docker is the obvious home.

And sometimes you want a Firecracker microVM that pauses when idle and resumes on the next request. DigitalOcean MicroVM does that in MKC1. Sprites gives you persistent Firecracker VMs on Fly.io. Those pause-and-resume properties belong to the provider. Cast does not invent them. It just makes them a --provider flag instead of a weekend of reading docs.

I like that framing because it keeps Cast honest. The hard product is the create and change loop. The hard infra is already out there.

The boring pieces that make shipping real

A deploy button is not enough. What made agents feel unfinished for me was everything around the first ship.

Agent versioning is one of those pieces. Cast keeps automatic snapshots, lets you cut intentional semantic releases, shows diffs, and can roll back to an earlier state. That is the same muscle as app deploys. If changing an agent's instructions feels permanent and scary, you will not change them. If rollback is one step, you will ship the small edit.

Credentials are another. There is an OAuth credential vault and secure token storage so secrets are not sitting in plain config. I have burned myself enough times copying keys into files that get committed, logged, or pasted into a chat. The vault is not glamorous. It is the difference between an agent you are willing to leave running and one you treat like a science fair project.

Deployment tracking sits next to that. You should be able to see what went where, and when. GitHub and git ops for agents are there too, so the agent can live in a repo with the usual init, commit, push, pull, and branch flow. Persistent agent memory covers the other half of "this should feel like an app": context that survives across sessions instead of resetting every time you start the process.

None of that is the demo that gets screenshots. It is the reason I trust the tool with agents I actually want to keep.

Closer to creating an app

I did not set out to invent a new kind of agent. I set out to shrink the distance between "this works in a session" and "this is a thing I can point at, change, and redeploy."

That distance is still where a lot of agent projects die. The model call is fine. The tools are fine. The week after, when you want to move it off your laptop, rotate a key, or undo a bad instruction change, the project turns into archaeology.

Cast Agent is my answer to that. Describe the agent. Get a scaffold. Deploy it to a provider you already use. Keep versions, credentials, and deploys in the open where you can see them.

Creating an agent should feel closer to creating an app. That is the bar I am building toward, one boring piece at a time.
