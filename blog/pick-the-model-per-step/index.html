I Stopped Picking a Model. I Pick One Per Step.

November 12, 2026

Most agent work is a lot of small, boring calls and a few hard ones, so I give the plan and the hard calls to a strong model, the rest to a cheaper one, and only escalate on evidence.

For a long time my model choice was a project setting. I picked the best model I could afford, pointed the agent at it, and every call went to the same place. Planning, tool calls, reformatting a JSON blob, deciding whether a test passed. Same model, same price, same latency.

That made sense when I was running one agent in one terminal. It makes a lot less sense now that I run several agents for my side projects, every day, on schedules. Once you look at what those agents actually spend their calls on, the "one model per project" habit starts to look like paying a senior engineer to rename files.

Most agent calls are not hard

When I read through agent traces, the pattern is the same almost every time. There are a few calls that matter a lot: understanding the task, writing the plan, making the judgment call when something unexpected happens, and reviewing the result. Then there are many calls that are mechanical: read this file, extract these fields, summarize this page, check whether this output matches a format, decide yes or no.

The hard calls are where a strong model earns its price. The mechanical calls mostly need to be fast, cheap, and reliable at following instructions and calling tools. Paying frontier prices for a yes or no answer is not quality. It is waste with a nicer label.

So I stopped asking "which model is best?" and started asking "which model is good enough for this step?"

How I split it

My default now looks like this.

A strong model for the plan and the hard calls. The agent that decides what to do, how to break up the work, and what "done" means gets the best model I have. Same for review. If a step is where a wrong call compounds into everything after it, that step gets the expensive seat.

A cheaper, faster model for the workers. The many small calls that execute a plan, fetch and shape data, or draft something that will be checked anyway go to a smaller model. These calls are the bulk of the volume, so this is where the bill actually moves.

A judge for the yes or no questions. A lot of agent loops are quietly full of decisions: did this pass, which tool fits, is this output in the right shape, should I retry. Those are classification problems, not writing problems. A model that picks one answer from a fixed set is a better fit than a model that wants to write you an essay about it.

None of this is exotic. It is the same thing any team does with people. You do not send every question to the most senior person in the room. You send them the questions only they can answer.

The rule that keeps it honest: escalate on evidence

The first time I split work across model tiers, I made the obvious mistake. I let each step decide for itself whether it was hard enough to need the bigger model.

Every step decided it was hard.

That is not the model being sneaky. If you ask "is this task difficult?" and give an easy way out, you get a cautious answer. The result was that the cheap tier barely got used and the bill drifted right back up.

What fixed it was an escalation rule based on evidence, not on how the task feels. A step starts on the cheaper model. It only gets bumped to the stronger one after something concrete goes wrong: a test fails, a check rejects the output, or the same step misses twice. If the cheap model gets it right, which it usually does for this kind of work, nobody needs to know the strong model exists.

This also gives me a useful signal. If a particular step escalates all the time, that step was never mechanical. I move it up a tier on purpose instead of paying for retries forever.

More effort is not the same as a better model

Another trap I fell into was cranking the reasoning effort on a small model and expecting big-model results. In my experience it mostly buys longer chains of thought and more retries, not better judgment. If a step needs judgment, give it a model with judgment. If it does not, give it a small model at normal effort and let it be fast.

The reverse is also true. For most of my day-to-day agent work, a strong general model at medium or high effort is plenty. I do not need the maximum setting for every call, and the "fast" variants are not always the bargain they look like when they get the hard calls wrong and you pay for the cleanup.

What this changes about building agents

Thinking per step changes how I structure agents in the first place.

It pushes me to make steps explicit. If the plan, the work, and the check are all one giant prompt, there is nothing to route. Once they are separate steps, each one can get the right model, the right tools, and the right budget.

It makes cost something I can reason about. Instead of "this agent is expensive," I can see which step is expensive and why. Usually it is one or two steps, and usually they are the ones I would have guessed.

And it makes swapping models less scary. New models show up constantly. When a new fast, cheap model lands, I do not have to migrate a whole agent and hope. I try it on the worker seat, run the same checks, and keep it if it holds up. The strong seat can stay where it is until something clearly better shows up there too.

This is also part of why I care about tooling that treats an agent as a set of parts you can change, not a single prompt glued to a single model. It is a big part of what I am building toward with Cast Agent: making it easy to create and deploy an agent, then change pieces of it later without starting over.

The short version

Do not pick a model for the project. Pick one for each step.

Give the plan and the hard calls to a model that can think. Give the volume to a model that is fast and cheap. Give the yes or no questions to something built to decide. And only escalate when the evidence says so, because if you let every step decide it is special, every step will.
