The Most Useful Button I Gave My Agent's Drafts Is "Send It Back"

November 16, 2026

Approve and reject were too blunt for reviewing an agent's drafts, so I added a third option that returns the draft with a note, and the details of that loop turned out to matter more than the button.

I have an agent that writes drafts of my posts on X. It does not post them. It sends them to xpost, a small scheduler I run at post.scottmiller.io, and every draft waits there until I approve it. The agent's token can propose drafts, and nothing it holds can approve or publish.

That part worked. What did not work at first was the review itself.

Approve or reject is a bad interface

When I opened the queue, each draft gave me two choices. Approve it and it goes out at its proposed time. Reject it and it is gone.

Most drafts were not either of those. They were close. The idea was right and one line was off. The tone was a little too much like a press release. A point was buried at the end that should have been first. A link was in a post that did not need one, and on the X API a post with a URL costs a lot more than a plain one, so that matters to me.

With only two buttons I had two bad options. I could approve something I did not quite like, or I could reject it and lose a draft that was most of the way there. The third option was to open the editor and fix it myself, which works, but then I am the writer again and the agent learns nothing from the exchange.

So I added a third button: send it back, with an optional note.

What "send it back" actually does

When I send a draft back, xpost calls a webhook that belongs to the agent. The payload carries the draft's current text, my note, an expiry time, and a callback the agent uses to answer. The agent rewrites the draft and posts the new text to that callback. The revised draft shows up in my queue again, still pending, still needing my approval.

The button is simple. The rules around it are where most of the thinking went, and I think they apply to any loop where a person reviews an agent's work.

The rules that made it trustworthy

The request is signed and short lived. Every webhook call carries a timestamp and an HMAC signature over the timestamp and the raw body. The receiver is told to check the signature with a constant time compare and to refuse anything more than five minutes old. A rewrite request is an instruction to an agent, and I do not want anyone else able to forge one.

xpost will not call just any address. The webhook has to be https on a public address. xpost refuses private ranges, loopback, link local and other reserved addresses when it connects. A feature that makes my server send requests to a URL I typed in is exactly the kind of thing that turns into a hole later, so I closed that off up front.

Answer fast, work later. The receiver should return a 2xx right away and do the rewrite afterward. Rewriting takes a model call, and a webhook sender that sits waiting on a model is a timeout waiting to happen.

There is a deadline. The agent has 60 minutes to reply. After that the request expires. I would rather have a stale request die quietly than get a rewrite hours later for a post whose moment has passed.

A 409 means stop. If I rejected the draft in the meantime, cancelled the request, sent a newer one, or the request already got an answer, the callback returns 409. The agent is told plainly not to retry a 409. This is the rule I care about most. An agent that keeps retrying after I changed my mind is worse than one that never answered.

"No changes" is a valid answer. The agent can send the same text back. xpost shows me "No changes" instead of treating it as an error. Sometimes my note is a question, or the draft really is fine, and I want the agent to be able to say so instead of inventing an edit to look busy.

The scope stays narrow. Revising needs its own scope on the token. The agent can only revise its own drafts, and only while they are pending. It can change the text and the number of parts in a thread, but it cannot change the images. And after a rewrite, the draft is still just a draft. Sending something back never moves it closer to publishing without me.

Why this beats editing it myself

The obvious objection is that it would be faster to fix the line myself. For a single draft, often it is.

But the note is the useful part. "Too salesy, lead with the problem" is a sentence I can write in five seconds, and it says something about how I want to sound that a silent edit does not. The agent gets the note next to the text it wrote, which is the right context for the fix. When I edit a draft myself, the agent only ever sees the final version, if it sees anything at all.

It also keeps the roles clean. The agent writes. I review. If I find myself rewriting a lot of drafts by hand, that is a signal the instructions are wrong, and I would rather find that out from my notes than bury it in my own edits.

What I would tell someone building a review loop for agents

Do not stop at approve and reject. Most agent output lands in the middle, and you need a cheap way to say "close, fix this."

Put the rules in the system. Signatures, expiry, a deadline, a clear "do not retry" signal, and a narrow scope are all things the software enforces. None of them depend on the agent behaving well.

Let the agent say nothing changed. A loop that forces an edit on every round trains an agent to make edits, not to make things better.

And keep the person at the end. A rewrite is just another draft. The approve button still belongs to me, and that is the one rule I do not plan to change.
