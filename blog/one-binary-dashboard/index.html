I Built My X Dashboard as One Binary, and the Agent Kept It That Way

October 19, 2026

How I built xstats, a small self-hosted X stats dashboard, with Grok Bot's help, and why keeping it to one Go binary and one SQLite file made the agent a better collaborator.

I wanted a simple thing: a page that shows how my X accounts are doing. Follower count, how that number moved over the last week and month, and how each recent post performed. I did not want another SaaS login, another monthly bill, or another dashboard that does forty things when I need four.

So I built one. It is called xstats, it is open source under MIT, and I built it with Grok Bot's help. The part I want to write about is not the dashboard itself. It is how much easier it was to work with an agent once I decided the whole thing had to stay small.

The constraint: one binary, one file of data

The rule I set at the start was that xstats ships as a single Go binary. The frontend is static HTML and JS, embedded into the binary with go:embed. Storage is SQLite through modernc.org/sqlite, which is pure Go, so the build runs with CGO_ENABLED=0 and there are no runtime dependencies to install on the server.

That gives you a very short list of moving parts:

  • xstats serve, listening on localhost
  • xstats.db, one SQLite file
  • Caddy in front, handling TLS and basic auth

That is the whole system. The server it runs on can be tiny. The README says 512 MB is plenty, and it is, because there is almost nothing there.

I have built enough software to know that the size of a system is mostly a decision you make early and then defend. What surprised me is how much that decision mattered for the agent, not just for me.

Small systems are easier to hand to an agent

When the whole app fits in your head, it also fits in the agent's context. There is no service mesh to explain, no ORM conventions to follow, no five-repo dance to make one change. I could describe a change in a couple of sentences and the agent had everything it needed to make it.

A good example: the first version had two buttons to switch between accounts. I asked for a dropdown instead, ordered by an optional XSTATS_ACCOUNTS setting, working in both light and dark themes and on a phone. That came back as one focused commit. It touched the parts it needed to and nothing else, because there was nothing else to touch.

Another one: I wanted to see "today," not just finished days. The data model stores one row per account per day and one row per post per day, and re-ingesting a day upserts. So instead of inventing a new hourly pipeline, the fix was to push the same day more than once and make sure a re-push fully replaces that day's post rows. The chart labels today's point as in progress. Small change, real test added, done. A bigger system would have tempted both of us into building something more clever than the problem required.

This connects to something I wrote about before: boring agents win. Boring systems win too, and they are the ones agents are actually good at changing.

The dashboard does not call the X API

One design choice I like a lot: xstats never talks to X. It has an ingest endpoint, POST /api/ingest, that takes a JSON bundle with a bearer token. The bundle is just the X API v2 responses saved as they came back, so you do not have to reshape anything.

That split exists for a practical reason. The data collection runs as a Grok Bot routine, because that is where I have X read access. The server just stores and draws. If I ever want server-side polling with my own developer credentials, that is a separate decision, and the dashboard does not care where the JSON came from.

It also means the dashboard holds no X credentials at all. The only secret on the server is the ingest token, and the push script reads it from a file and hands it to curl on stdin so it never shows up on a command line. The dashboard password is sent over SSH stdin and hashed on the server with caddy hash-password, so only the bcrypt hash is stored.

None of that is fancy. It is the kind of thing you get right when the system is small enough that you can actually see every place a secret could leak.

Deploys you are not afraid of

The deploy script targets a fresh Ubuntu server and is idempotent. Nothing gets compiled on the server. You build locally, run deploy.sh, and it installs Caddy from its official repo, creates a system user, drops in the binary and a systemd unit, and writes the token with tight permissions.

Two small details make it feel safe to run often. Each deploy keeps the previous binary around as xstats.prev, and it backs up the database with a timestamp before touching anything. If a change goes sideways, rollback is one copy and a restart.

When an agent is making changes for you, this matters more than usual. I approve the pull requests, but I want the cost of a bad merge to be a minute of my time, not an evening. Cheap rollback is what lets me say yes faster.

What I would tell someone building with agents

A few things I took away from this one:

  1. Pick the boring stack on purpose. Go, SQLite, a reverse proxy. The agent knew all of it well, and so did I, which made review quick.
  2. Keep the data format dumb. Raw API responses in, upserts by day. Rerunning is always safe, which means mistakes are cheap.
  3. Separate collection from display. The thing with credentials and the thing with a web page should not be the same thing.
  4. Use fake data for anything public. The screenshots in the README come from a seed script that generates made-up accounts. I never had to scrub a real screenshot.
  5. Make every change a small PR. The history of xstats is a handful of commits, each one about one thing. That is easy to read later, for me and for the next agent.

Try it

If you want your own little X stats page, the repo is at github.com/scott/xstats. It is one binary, it runs on a small server, and it does not try to be anything more than it is. These are my own views and my own side project.

If you build something on top of it, or strip it down even further, I would like to see it.
