Review the Plan, Not Just the Diff

October 29, 2026

Why the cheapest place to catch an agent's mistake is the markdown plan it writes before any code, and why I built Gander to get a second person onto that plan.

Most of the conversation about reviewing agent work is about the diff. Did the tests pass, is the code readable, did it touch files it should not have. That review matters. But by the time I am reading a diff, the most important decisions were already made, usually a few minutes earlier, in a markdown file nobody else looked at.

When I ask a coding agent for anything bigger than a small fix, the first useful thing it produces is a plan. Sometimes it is called plan.md, sometimes it is a spec or a design note or a runbook. It says what the agent thinks the problem is, which files it will change, what it will leave alone, and in what order. Then it starts writing code against that plan.

That file is where I want a second set of eyes. Here is why, and what I built to make it easier.

A wrong plan produces confident, wrong code

An agent that misunderstands the task does not write broken code. It writes clean, well-structured code that solves a slightly different problem. The tests it writes agree with it, because they were written from the same misunderstanding. The diff looks good. The PR description is articulate. And the thing is still wrong.

You can catch that in code review, but it is expensive there. You are reading hundreds of lines to reverse-engineer a decision that was stated in one sentence of the plan. Then you ask for changes, and the agent rewrites a lot of code that was never the problem.

In the plan, the same mistake is one line. "I will add a new table for this" when you already have one. "I will handle this in the client" when it belongs on the server. "Out of scope: migrations" when the whole point was the migration. Fixing it is a comment and a rewrite of a paragraph. Nothing has been built on top of it yet.

So my view is simple. The plan is the cheapest place to fix an agent's mistake, and it is the place we review the least.

Why plans go unreviewed

It is not that people do not care. It is that the plan lives in the worst possible place for review.

It is a file on the author's machine, inside a session only the author can see. If I want a teammate to look at it, my options are all bad:

  • Share my screen and scroll through it while they squint.
  • Paste it into a chat or a doc, which freezes a copy while the real file keeps changing.
  • Commit it early so they can review it in git, which turns a ten minute question into a branch and a PR.
  • Skip the second reviewer and review it myself, in the same session that wrote it.

The last one is what usually happens. And reviewing a plan alone, right after asking for it, is the review most likely to agree with the agent. I asked the question, so I read the answer the way I meant the question.

Even when I do get someone to read it, their feedback has to get back to the agent somehow. That usually means me copying comments out of a chat thread and pasting them into the prompt, which is exactly the kind of chore that makes people stop doing it.

What I wanted instead

I wanted three things, and I wanted all three, because any one of them alone does not change the habit.

First, a live link to the file the agent is still writing. Not a snapshot. If the agent edits the plan while someone is reading it, they should see the edit.

Second, comments on the actual lines of the rendered document, the way people already comment on docs. Not a chat box about the whole page. A reviewer should be able to highlight "I will add a new table" and say "we already have one, use it."

Third, those comments have to reach the agent without me in the middle. If a reviewer writes a comment addressed to the agent, the agent in my session should see it, act on it, and update the file. The link updates too, so the reviewer sees their comment land.

That is what Gander is. You run gander watch plan.md, you get a short link that live-updates on every save, and you send that link to whoever should look. They open it in a browser. They do not need my IDE, my repo, or an account in my agent setup. They comment inline. Comments addressed to @agent come back into the agent session through MCP after a one-time gander mcp install, and gander comments is there as a fallback if you want to pull them by hand.

The local file stays the source of truth. Gander does not replace git and it is not a pull request tool. Once the plan is good and the code is written, the normal PR process takes over. Gander is for the loop before that, while the plan is still cheap to change.

What changes when the plan gets a reviewer

The biggest change is not speed. It is where disagreements happen.

When a teammate reads the plan, the arguments move earlier. "Should this be a new service" gets settled before there is a new service. "Do we need this at all" gets asked before the agent spends its effort building it. The code review that follows gets smaller and more boring, which is what I want from code review.

It also changes how I prompt. Knowing someone else will read the plan pushes me to ask the agent for plans that a human can actually review: what it will change, what it will not change, and what it is unsure about. A plan with an explicit "open questions" section is far easier to comment on than a wall of steps.

And it keeps the agent honest in a way self-review does not. A reviewer who was not in the conversation does not share my assumptions. They read the plan cold, the same way the code will eventually be read cold by whoever maintains it.

The habit, not the tool

If you take one thing from this, it is not "use my product." It is this: before an agent writes a lot of code, get one other person to read the plan, and make it easy for their feedback to reach the agent.

You can do that with a screenshare if you have to. I built Gander because I wanted it to take one command and one link, so I would actually do it every time instead of only when the stakes felt high. The stakes are usually higher than they feel at the planning stage. That is the whole point of reviewing there.
