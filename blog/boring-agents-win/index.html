Boring Agents Win

July 21, 2026

The agents that ship in production are the ones nobody wants to demo.

Everyone wants to build a flashy agent. The one that plans, reasons, calls nine tools, reflects on its mistakes, and writes a beautiful trace you can show off at a meetup. Then it crashes on a malformed JSON response at 2am and you've got nothing.

I've spent the last year building and shipping agents, and the lesson I keep relearning is this: boring agents win. The agent that does one thing, every time, with a clear input and a clear output, will outperform the clever one in production every single time. Not because the clever one is dumb — it's usually smart. But because the boring one is reliable, debuggable, and predictable. And in production, those three things matter more than intelligence.

Here's what I've seen work.

One job per agent. An agent that "handles customer support" is a research project. An agent that "extracts order IDs from emails and writes them to a spreadsheet" is a product. The narrower the scope, the better the agent. The model doesn't get confused, the prompt doesn't grow to 4,000 tokens, and you can actually test it. When the scope creeps, quality collapses. Every teammate who's shipped agents has this story.

Determinism where it matters. Agents are probabilistic. That's their nature. But the parts around the agent don't have to be. The trigger, the input formatting, the output validation, the retry logic, the fallback when it fails — all of that should be code, not vibes. Treat the LLM call like a function with a type signature, even if the function sometimes returns garbage. The discipline of "this is what good input looks like" and "this is what valid output looks like" is what makes an agent production-grade.

No tool spam. Giving an agent 30 tools and saying "figure it out" is a great way to burn a lot of tokens and get bizarre results. Tools should be coarse-grained and named clearly. "search_docs" is better than three different retrieval tools. "send_email" is better than "compose_email" + "lookup_recipient" + "validate_address". The agent's job is to decide what to do, not to navigate your internal API design.

Logs you actually read. A good agent system produces a log line per step that a human can skim. What was the input? What did the model decide? Which tool got called? What came back? Did the output pass validation? If the answer to any of these is "I dunno, check the trace in the UI," you will hate your life when something breaks. Boring agents have boring logs. Boring logs save you at 2am.

Timeouts and budgets, ruthlessly. Every agent call needs a hard timeout. Every task needs a token budget. Every workflow needs a max number of steps. Without these, an agent can spiral — looping on the same failure, retrying forever, burning through your API budget on a single stuck request. The boring answer is to put a ceiling on everything and have a clear "if this fails, do X" path. It's not elegant. It works.

The temptation, especially when you're building something new, is to show off. To make the agent do something impressive. To demonstrate that it can plan, adapt, handle ambiguity. And yeah, that's fun. But the agents that actually run in production for months at a time are the ones where the team sat down and said "what's the smallest, most reliable version of this we can ship?" Then they shipped that, watched it run, and improved it based on what actually broke — not what they imagined might break.

The flashiest demo agents are the ones that get blog posts and conference talks. The boring agents are the ones that still work six months later, that the team trusts, that handle a million requests without anyone having to think about them. Those are the ones I want to build.

Boring wins. Ship the boring version. Iterate from there.
